Training a large model means splitting each step across many devices. Those devices then have to exchange data, and that communication can limit how fast the step runs. This post covers seven ways to split the work and what each one has to move.

Most of the post uses one linear layer as its example:

$$
X[T, E] \; @ \; W[E, E] \rightarrow Y[T, E]
$$

<MatmulExample client:visible />

$X$ is the input, $W$ is the weights, and $Y$ is the output. $T$ is the number of token rows, and $E$ is the hidden width. This matmul takes about $2TE^2$ operations. The backward pass computes two more matmuls of the same size, for $\partial X$ and $\partial W$, so a training step takes about $6TE^2$. We split this work across $P$ devices.

A *roofline* analysis bounds a device's speed by two limits: its peak compute rate, and the rate at which data can reach it. The lower limit sets the speed. The original roofline model used memory bandwidth for the second limit, and here we use the network. To see which limit is likely to apply, each section works out one ratio:

$$
\frac{\text{operations per device}}{\text{values moved per device}}
$$

We count one layer over a full training step. A higher ratio means each value moved supports more computation. The network becomes the limit when the ratio falls below the device's peak operations per second divided by the values per second its network delivers. The counts are rough and drop small factors such as $(P-1)/P$, so they show how a method responds to changes in $T$, $E$, and $P$ more than exactly where a real system hits that limit.

Timing matters too. When a transfer overlaps with computation, the two take about as long as the slower one. When computation has to wait for the transfer, they take as long as both combined.

Each section covers the same points in the same order: what is split, what moves, whether the transfer can overlap with computation, the ratio, and the limit. A *collective* is a communication operation involving every device in a group, and the [appendix](#appendix-collectives) animates each one.

## Data parallelism

Data parallelism splits the token rows. Every device keeps a full copy of $W$ and processes $T/P$ rows:

$$
X[T/P, E] \; @ \; W[E, E] \rightarrow Y[T/P, E]
$$

<ShardingStage strategy="dp" client:visible />

Nothing moves in the forward pass. In the backward pass, each device gets a different gradient $\partial W$ because it saw different rows. The devices combine their gradients with an [all-reduce](#all-reduce), which sums values across devices and gives every device the result.

These all-reduces can overlap with computation. Only the optimizer needs the summed gradient, and it runs at the end of the step, so each all-reduce can run while the backward pass continues through earlier layers. The last all-reduce has no computation left to overlap with.

<Timeline schedule="dp" client:visible />

Each device computes $\sim 6TE^2/P$ operations, and an all-reduce moves $\sim 2E^2$ values per device, so the ratio is about $3T/P$.

The limit is memory. Splitting rows reduces the activations each device stores, but every device still stores all of the weights, gradients, and optimizer state.

## FSDP

Fully sharded data parallelism (FSDP) splits the rows the same way, and also splits the weights, gradients, and optimizer state. A device stores only $E^2/P$ of a layer's weights. To run the layer, the devices use an [all-gather](#all-gather), which gives every device all of the pieces, to build a temporary full copy of $W$.

<ShardingStage strategy="fsdp" client:visible />

Each layer has three transfers: an all-gather of $W$ in the forward pass, another in the backward pass, and a [reduce-scatter](#reduce-scatter) of $\partial W$, which sums values across devices and leaves each device with one piece of the result. Together, they move about 1.5 times as much data as data parallelism's all-reduce. Keeping the gathered $W$ through the backward pass removes one all-gather but uses more memory.

A device can gather the next layer's weights while it computes the current layer. If the gather finishes first, computation never waits for it. Only the first gather and the last reduce-scatter have no computation to overlap with.

<Timeline schedule="fsdp" client:visible />

Compute is the same as data parallelism, $\sim 6TE^2/P$. The three transfers move $\sim 3E^2$ values, so the ratio is about $2T/P$.

FSDP saves memory but moves 1.5 times as much data. The limit is that a device must hold one layer's full weights while the layer runs, plus the next layer's when gathering ahead. With few rows per device, the gathers can also take longer than the compute they overlap with, and computation starts waiting.

## Tensor parallelism

Tensor parallelism splits a matrix axis instead of the rows, and it has two forms.

A column-parallel layer splits $W$ by output columns. Every device has all of $X$ and computes its own columns of $Y$:

$$
X[T, E] \; @ \; W_i[E, E/P] \rightarrow Y_i[T, E/P]
$$

<ShardingStage strategy="tp-col" client:visible />

A row-parallel layer splits $W$ by rows and needs $X$ split by columns to match. Each device computes a full-sized output, but it is only a partial sum. The real $Y$ is the sum across all devices:

$$
X_i[T, E/P] \; @ \; W_i[E/P, E] \rightarrow Y^{(i)}[T, E]
$$

<ShardingStage strategy="tp-row" client:visible />

The output of a column-parallel layer is exactly the input a row-parallel layer needs, even with an elementwise nonlinearity between them. So a column-parallel layer followed by a row-parallel layer needs nothing moved between them. It needs one collective at the end, usually an all-reduce, because the layers between pairs need all of $Y$. A reduce-scatter can instead leave each device with some rows of $Y$, as in the diagram above, with an all-gather rebuilding $Y$ before the next pair. This moves the same amount of data, and the layers in between work on $1/P$ of the rows. The backward pass also needs one collective per pair.

<TpPair client:visible />

That final collective normally makes computation wait, because the next layer needs its result. It can overlap if the layer is computed in chunks of rows: each chunk's all-reduce runs while the next chunk computes. The implementation has to split the matmul and start each chunk's transfer as soon as the chunk is done, so this isn't automatic.

<Timeline schedule="tp-chunks" client:visible />

For a pair of layers, each device computes $\sim 12TE^2/P$ operations. The pair's two all-reduces, one in each pass, move $\sim 4TE$ values per device. $T$ cancels, so the ratio is about $3E/P$.

The limit is group size. As $P$ grows, each device's matmul gets narrower, but the activation it has to move stays the same size.

## Context parallelism

Context parallelism splits sequence positions. With $N$ sequences of length $S$, $T = NS$, and each device holds $S/P$ positions of each sequence. Dense layers treat positions as rows, so they split and communicate like data parallelism.

Attention is different, because each device's queries need keys and values from positions it doesn't hold. Attention tensors have shape $[N, A, S, H]$, where $A$ is the number of heads, $H$ is the head width, and $E = AH$. There are two common ways to provide the missing data.

### Ring attention

Ring attention keeps the position split. Each device holds one block of each attention tensor:

$$
Q, K, V: [N, A, S/P, H]
$$

$Q$ stays where it is, and $K,V$ blocks pass from device to device around a ring. Each device computes with every block as it arrives and updates its softmax as it goes, so the output exactly matches full attention. In the diagram, colors show which device each block started on.

<RingAttention client:visible />

A device can send a block while it computes with that block. This overlap works if each transfer finishes within one block's compute time and the network can carry all of the neighbor transfers at once.

For each block in the forward pass, a device computes $\sim 4NA(S/P)^2H$ operations and sends $\sim 2NA(S/P)H$ values. The backward pass computes and sends about twice as much, so the ratio is about $2S/P$.

The limit is balance. With a causal mask, later positions attend to more keys than earlier ones, so compute is uneven unless positions are reassigned across devices.

### Ulysses attention

Ulysses changes the split so that attention can run locally. An [all-to-all](#all-to-all), in which every device sends a different piece to every other device, swaps the position split for a head split:

$$
[N, A, S/P, H] \rightarrow [N, A/P, S, H]
$$

<UlyssesAttention client:visible />

Each device now holds every position for $A/P$ heads and computes attention locally. A second all-to-all returns the output to the position split.

Both all-to-alls normally make computation wait: attention can't start until the first finishes, and the next layer can't start until the second finishes. Splitting each exchange into chunks can overlap part of it with computation, but this takes a custom implementation.

The exchanges move $\sim 4NA(S/P)H$ values per device in each pass: $Q$, $K$, $V$, and the output in the forward pass, and their gradients in the backward pass. Local attention computes $\sim 4N(A/P)S^2H$ operations in the forward pass and about twice that in the backward pass. $P$ cancels, so the ratio is about $1.5S$.

The limit is the number of heads. $P$ can't exceed $A$, and the split is only even if $P$ divides $A$. Grouped-query and multi-query attention have fewer $K,V$ heads, which can lower this limit or require a different implementation.

Per device, ring attention moves about $P/2$ times more data than Ulysses in the forward pass, and about $P$ times more in the backward pass. But it can overlap those transfers with computation. Ulysses moves less, but computation waits for it. The timeline shows a forward pass on 4 devices.

## Expert parallelism

A mixture-of-experts layer has many feed-forward experts, and a router sends each token to $k$ of them. Expert parallelism splits the experts across devices. As in the example, we treat each expert as one $E \times E$ layer. Each device starts with $T/P$ tokens, and there are two ways to bring tokens and experts together. Both diagrams use $k = 2$.

### All-to-all routing

One all-to-all sends each token to the devices holding its $k$ experts. A second all-to-all returns the outputs. Routes are usually uneven, so the transfers need variable sizes or padding up to a fixed capacity.

<ExpertRouting method="all-to-all" client:visible />

Neither transfer overlaps with computation by default. An expert can't start until its tokens arrive, and the combined output has to wait for the slowest expert.

Each token-expert pair computes $\sim 2E^2$ operations in the forward pass and $\sim 4E^2$ in the backward pass. Each pass sends the pair's $E$ values out and back, $\sim 4E$ in all. Both counts scale with $k$ and $T/P$, so the ratio is about $1.5E$.

The limit is load balance. When a *hot expert* receives far more than its share of tokens, the whole group waits for that device. The toggle above shows this case.

### All-gather and reduce-scatter routing

This method sends every token to every device with an all-gather. Each device computes the tokens routed to its experts, applies the weight the router gave each expert, and writes zeros for all other tokens. A reduce-scatter then sums the contributions and returns each token's result to the device it started on.

<ExpertRouting method="gather-scatter" client:visible />

Both transfers can overlap with computation if they are chunked: the experts process chunks as they are gathered, and finished chunks go into the reduce-scatter. As with tensor parallelism, the implementation has to start each chunk's transfer as soon as the chunk is ready.

With balanced routing, each device computes $\sim 6kTE^2/P$ operations. Each pass has a gather and a scatter of $\sim TE$ values, $\sim 4TE$ in all, so the ratio is about $1.5kE/P$.

The limit is data volume. All-to-all routing moves $\sim kTE/P$ values per device in each transfer, so this method moves about $P/k$ times more per device. The gap shrinks as $k$ grows, and it can be smaller in practice, because all-to-all messages share network links and may need padding. Every device also needs room for all $T$ tokens unless chunks are streamed. It doesn't fix load imbalance either, so a hot expert still slows the group.

## Summary

Each method splits different work, so each ratio depends on different numbers.

| Method | Split | Communication | Overlap | Ratio | Memory saved |
| --- | --- | --- | --- | --- | --- |
| Data parallelism | Token rows | All-reduce $\partial W$ | Yes, except the last | $3T/P$ | Activations |
| FSDP | Token rows, model state | Two all-gathers of $W$, reduce-scatter $\partial W$ | By gathering ahead | $2T/P$ | Activations, model state |
| Tensor parallelism | Hidden width | One all-reduce per pair in each pass | With chunking | $3E/P$ | Model state, some activations |
| Ring attention | Positions | Neighbor transfers of $K,V$ | If each send fits in one block's compute | $2S/P$ | Activations |
| Ulysses attention | Positions, then heads | Two all-to-alls | Not by default | $1.5S$ | Activations |
| Expert all-to-all | Experts | Two all-to-alls | Not by default | $1.5E$ | Expert weights, activations |
| Expert gather/scatter | Experts | All-gather, reduce-scatter | With chunking | $1.5kE/P$ | Expert weights |

Overlap and a high ratio help in different ways. Overlap stops a transfer from making computation wait. A high ratio keeps a transfer small compared with the computation, even when computation has to wait. Ulysses and all-to-all routing rely on a high ratio.

<RatioExplorer client:visible />

Move the sliders to see how the ratios respond. The bars use the estimates above, including constants, and ignore hardware and limits on $P$, such as Ulysses needing $P \le A$. They show how the ratios scale, not how fast a real system runs.

## Combining methods

Large training runs use several methods at once. They arrange the devices in a mesh and give each method one axis. Here, 8 devices form a $2 \times 4$ mesh, with tensor parallelism across each row and data parallelism down each column.

<DeviceMesh client:visible />

Each collective runs only within its group. A tensor-parallel collective involves the 4 devices in a row, and a gradient all-reduce involves the 2 devices in a column. Each ratio then depends on its own group size: with $P_t$ devices in a row and $P_d$ in a column, the ratios are about $3E/P_t$ and $3T/P_d$. You can compute each ratio separately, but with a fixed number of devices, growing one group shrinks the other, and both transfers share the network.

## Appendix: collectives

Every method except ring attention uses these four collectives. Ring attention sends $K,V$ blocks only between neighbors. Each diagram shows 4 devices. The first three use a ring, in which each device sends only to the next device.

### All-gather

Every device starts with one piece and ends with all of them. Each device receives the $P-1$ pieces it doesn't have.

<Collective kind="all-gather" client:visible />

### Reduce-scatter

Every device starts with its own partial sum of every piece. Each device ends with one piece, summed over all devices. Each device sends $P-1$ pieces.

<Collective kind="reduce-scatter" client:visible />

### All-reduce

Every device ends with the full sum. A ring all-reduce runs a reduce-scatter and then an all-gather, so it moves twice as much data as either one.

<Collective kind="all-reduce" client:visible />

### All-to-all

Every device starts with one piece for each device, and each piece goes to the device it's for. Each device sends $P-1$ pieces and keeps one.

<Collective kind="all-to-all" client:visible />
