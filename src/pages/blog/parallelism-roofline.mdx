Training a large model means splitting each step across many devices. Those devices then have to exchange data, and that communication can limit how fast the step runs. This post covers seven ways to split the work and what each one has to move.

Most of the post uses one linear layer as its example. Its input is a batch of $B$ sequences, each $S$ tokens long, and each token is a vector of $E$ values:

$$
X[B, S, E] \; @ \; W[E, F] \rightarrow Y[B, S, F]
$$

$X$ is the input, $W$ is the weights, and $Y$ is the output. $E$ is the input width and $F$ is the output width. The matmul treats each of the $BS$ tokens as one row. Each entry of $Y$ is the dot product of a row of $X$ and a column of $W$: $E$ multiplications and $E - 1$ additions, or about $2E$ operations. $Y$ has $BSF$ entries, so the matmul takes about $2BSEF$ operations. The backward pass computes two more matmuls of the same size, for $\partial X$ and $\partial W$, so a training step takes about $6BSEF$. We split this work across $P$ devices.

<MatmulExample client:visible />

A *roofline* analysis bounds a device's speed by two limits: its peak compute rate, and the speed at which the bytes each operation needs can be moved to it. The lower limit determines where the bottleneck is and sets the overall time. To understand how parallelism affects the roofline, each section works out one ratio:

$$
\frac{\text{operations per device}}{\text{values moved per device}}
$$

We count values rather than bytes, for one layer over a full training step. A higher ratio means each value moved supports more computation. **The network becomes the limit when the ratio falls below the device's peak operations per second divided by the values per second its network delivers.**

Timing matters too. **When a transfer overlaps with computation, the two take about as long as the slower one. When computation has to wait for the transfer, they take as long as both combined.**

Each section covers the same points in the same order: what tensors are split, what tensors are communicated across devices, whether the comms can overlap with computation, the resulting ratio, and the overall effect (what the method shrinks on each device and how far it scales). A *collective* is a communication operation involving every device in a group, and the [appendix](#appendix-collectives) animates each one.

## Data parallelism

Data parallelism splits the batch. Every device keeps a full copy of $W$ and processes $B/P$ whole sequences:

$$
X[B/P, S, E] \; @ \; W[E, F] \rightarrow Y[B/P, S, F]
$$

<ShardingStage strategy="dp" client:visible />

Splitting the positions within each sequence instead is context parallelism, covered [below](#context-parallelism). For a linear layer the two splits behave the same, because each token is just a row. They differ in attention, which mixes the positions of a sequence. Data parallelism keeps each sequence on one device, so attention needs no communication.

Nothing moves in the forward pass. In the backward pass, each device gets a different gradient $\partial W$ because it saw different sequences. The devices combine their gradients with an [all-reduce](#all-reduce), which sums values across devices and gives every device the combined result.

These all-reduces can overlap with computation because the backward pass never waits for them. The backward pass runs from the last layer to the first, and each layer needs only $\partial X$ from the layer above it. Computing $\partial X$ uses $W$, not the summed $\partial W$. Only the optimizer needs the summed gradients, and it runs after the backward pass. So each all-reduce can start as soon as its layer finishes and run while the next layers compute. The last all-reduce has no computation left to overlap with.

<Timeline schedule="dp" client:visible />

Each device computes $\sim 6BSEF/P$ operations. An all-reduce has two halves, shown in the [appendix](#all-reduce). In the first, each device sends $P-1$ of the $P$ pieces of its $\partial W$, about $EF$ values, to the devices that sum them. In the second, each device sends its summed piece to the other $P-1$ devices, about $EF$ values again. So an all-reduce moves $\sim 2EF$ values per device whatever $P$ is, and **the ratio is about $\boldsymbol{3BS/P}$**.

Data parallelism cuts the sequences each device processes, and with them its compute and activations. It doesn't cut the weights, gradients, or optimizer state, which every device stores in full. It scales well because the all-reduces overlap with the backward pass. That holds until $BS/P$, the tokens on each device, gets too small for each layer's compute to hide its all-reduce.

## FSDP

Fully sharded data parallelism (FSDP) splits the batch the same way, and also splits the weights, gradients, and optimizer state. A device stores only $EF/P$ of a layer's weights. To run the layer, the devices use an [all-gather](#all-gather), which gives every device all of the pieces, to build a temporary full copy of $W$.

<ShardingStage strategy="fsdp" client:visible />

Each layer has three transfers: an all-gather of $W$ in the forward pass, another in the backward pass to compute $\partial X$, and a [reduce-scatter](#reduce-scatter) of $\partial W$. As in data parallelism, each device computes $\partial W$ from its own tokens, treated as $BS/P$ rows:

$$
X^\top[E, BS/P] \; @ \; \partial Y[BS/P, F] \rightarrow \partial W[E, F]
$$

The result is full size but only part of the sum. The reduce-scatter adds these partial results across devices and leaves each device only the summed piece that matches its piece of $W$. That is all its optimizer needs, because each device updates only its own piece of $W$. Data parallelism's all-reduce is the same reduce-scatter followed by an all-gather, which gives every device the whole sum.

<ShardingStage strategy="fsdp-grad" client:visible />

Each of the three transfers is half of an all-reduce, so each moves about $EF$ values per device. Together they move 1.5 times as much data as data parallelism's all-reduce. Keeping the gathered $W$ through the backward pass removes one all-gather but uses more memory.

A device can gather the next layer's weights while it computes the current layer. If the gather finishes first, computation never waits for it. Only the first gather and the last reduce-scatter have no computation to overlap with.

<Timeline schedule="fsdp" client:visible />

Compute is the same as data parallelism, $\sim 6BSEF/P$. The three transfers move $\sim 3EF$ values, so **the ratio is about $\boldsymbol{2BS/P}$**.

FSDP cuts the sequences each device processes, like data parallelism, and also cuts the weights, gradients, and optimizer state each device stores to $1/P$ of their full size. In exchange, it moves 1.5 times as much data, and a device must still hold one layer's full weights and unreduced $\partial W$ while the layer runs, plus the next layer's weights when gathering ahead. It scales until $BS/P$ gets too small for each layer's compute to hide its gathers.

## Tensor parallelism

Tensor parallelism splits the weights instead of the tokens, and it has two forms.

A column-parallel layer splits $W$ by output columns. Every device has all of $X$ and computes its own columns of $Y$:

$$
X[B, S, E] \; @ \; W_i[E, F/P] \rightarrow Y_i[B, S, F/P]
$$

<ShardingStage strategy="tp-col" client:visible />

A row-parallel layer splits $W$ by rows and needs $X$ split by columns to match. Each device computes a full-sized output, but it is only a partial sum. The real $Y$ is the sum across all devices:

$$
X_i[B, S, E/P] \; @ \; W_i[E/P, F] \rightarrow Y^{(i)}[B, S, F]
$$

<ShardingStage strategy="tp-row" client:visible />

The output of a column-parallel layer is already split by columns across devices, which is exactly the input a row-parallel layer needs. This holds even with an elementwise nonlinearity between them, because it works on each value separately. So a column-parallel layer followed by a row-parallel layer needs nothing moved between them. In the figure below, the pair is a feed-forward block: $W_1$ is $[E, F]$ and $W_2$ is $[F, E]$, so $F$ is the feed-forward width. $H[B, S, F]$ is the first layer's output and the second layer's input, and $Y[B, S, E]$ has the same shape as $X$:

<TpPair client:visible />

The pair needs one collective at the end, usually an all-reduce, because the layers between pairs need all of $Y$. This leaves $Y$ on every device, as $X$ was at the start. A reduce-scatter can instead leave each device with some of $Y$'s token rows, as in the row-parallel diagram above, with an all-gather rebuilding $Y$ before the next pair. This moves the same amount of data, and the layers in between work on $1/P$ of the tokens. The backward pass also needs one collective per pair.

That final collective normally makes computation wait, because the next layer needs its result. It can overlap if each device splits its work into chunks of token rows. These chunks don't come from the column or row split, which in the pair both split $F$: every device still has all $BS$ token rows. A row of the output depends only on the same row of the input, so a device can compute its rows one chunk at a time and all-reduce each chunk while the next one computes. The column-parallel layer can be chunked the same way, so each chunk can run through the whole pair before its all-reduce. The implementation has to split the matmul and start each chunk's transfer itself, so this isn't automatic.

<TpChunks client:visible />

For a pair of layers, each device computes $\sim 12BSEF/P$ operations. The pair's two all-reduces, one in each pass, move $\sim 4BSE$ values per device. $B$, $S$, and $E$ cancel, so **the ratio is about $\boldsymbol{3F/P}$**.

Tensor parallelism cuts each device's share of the weights and of each matmul, but not the tokens it processes. Its transfers don't shrink as $P$ grows: each device's matmul gets narrower, but the activation it moves stays the same size. So it suits small groups of devices, where $3F/P$ stays high.

## Context parallelism

Context parallelism splits the sequence: each device holds $S/P$ positions of every sequence. Dense layers treat each token as a row, so they split and communicate like data parallelism.

Attention is different, because each device's queries need keys and values from positions it doesn't hold. Attention tensors have shape $[B, A, S, H]$, where $A$ is the number of heads, $H$ is the head width, and $E = AH$. There are two common ways to provide the missing data.

### Ring attention

Ring attention keeps the position split. Each device holds one block of each attention tensor:

$$
Q, K, V: [B, A, S/P, H]
$$

$Q$ stays where it is, and $K,V$ blocks pass from device to device around a ring. Each device computes with every block as it arrives and updates its softmax as it goes, so the output exactly matches full attention. In the diagram, colors show which device each block started on.

<RingAttention client:visible />

A device can send a block while it computes with that block. This overlap works if each transfer finishes within one block's compute time and the network can carry all of the neighbor transfers at once.

For each block in the forward pass, a device computes $\sim 4BA(S/P)^2H$ operations and sends $\sim 2BA(S/P)H$ values. The backward pass computes and sends about twice as much, so **the ratio is about $\boldsymbol{2S/P}$**.

Ring attention cuts the positions each device holds, and with them its activations, so a sequence can be longer than one device could hold. It scales while each block's compute hides its send. As $P$ grows, a block's compute shrinks faster than its send, so this eventually fails. With a causal mask, later positions attend to more keys than earlier ones, so compute is also uneven unless positions are reassigned across devices.

### Ulysses attention

Ulysses changes the split so that attention can run locally. An [all-to-all](#all-to-all), in which every device sends a different piece to every other device, swaps the position split for a head split:

$$
[B, A, S/P, H] \rightarrow [B, A/P, S, H]
$$

<UlyssesAttention client:visible />

Each device now holds every position for $A/P$ heads and computes attention locally. A second all-to-all returns the output to the position split.

Both all-to-alls normally make computation wait: attention can't start until the first finishes, and the next layer can't start until the second finishes. Splitting each exchange into chunks can overlap part of it with computation, but this takes a custom implementation.

The exchanges move $\sim 4BA(S/P)H$ values per device in each pass: $Q$, $K$, $V$, and the output in the forward pass, and their gradients in the backward pass. Local attention computes $\sim 4B(A/P)S^2H$ operations in the forward pass and about twice that in the backward pass. $P$ cancels, so **the ratio is about $\boldsymbol{1.5S}$**.

Ulysses also cuts the activations each device holds, and its ratio, $1.5S$, doesn't fall as $P$ grows. But computation waits for its all-to-alls, and $P$ can't exceed the number of heads $A$. The split is only even if $P$ divides $A$. Grouped-query and multi-query attention have fewer $K,V$ heads, which can lower this limit or require a different implementation.

Per device, ring attention moves about $P/2$ times more data than Ulysses in the forward pass, and about $P$ times more in the backward pass. But it can overlap those transfers with computation. Ulysses moves less, but computation waits for it. The timeline shows a forward pass on 4 devices.

## Expert parallelism

A mixture-of-experts layer has many feed-forward experts, and a router sends each token to $k$ of them. Expert parallelism splits the experts across devices. We treat each expert as a pair of layers, $W_1[E, F]$ and $W_2[F, E]$, so a token arrives and leaves with $E$ values. Each device starts with $BS/P$ tokens, and there are two ways to bring tokens and experts together. Both diagrams use $k = 2$.

### All-to-all routing

One all-to-all sends each token to the devices holding its $k$ experts. A second all-to-all returns the outputs. Routes are usually uneven, so the transfers need variable sizes or padding up to a fixed capacity.

<ExpertRouting method="all-to-all" client:visible />

Neither transfer overlaps with computation by default. An expert can't start until its tokens arrive, and the combined output has to wait for the slowest expert.

Each token-expert pair computes $\sim 4EF$ operations in the forward pass and $\sim 8EF$ in the backward pass. Each pass sends the token's $E$ values out and back, $\sim 4E$ in all. Both counts scale with $k$ and $BS/P$, so **the ratio is about $\boldsymbol{3F}$**.

Expert parallelism cuts the expert weights each device stores, so adding devices allows more experts. Its ratio, $3F$, doesn't fall as $P$ grows, but the transfers don't overlap by default, and the group runs only as fast as its busiest device. When a *hot expert* receives far more than its share of tokens, the whole group waits for that device. The toggle above shows this case.

### All-gather and reduce-scatter routing

This method sends every token to every device with an all-gather. Each device computes the tokens routed to its experts, applies the weight the router gave each expert, and writes zeros for all other tokens. A reduce-scatter then sums the contributions and returns each token's result to the device it started on.

<ExpertRouting method="gather-scatter" client:visible />

Both transfers can overlap with computation if they are chunked: the experts process chunks as they are gathered, and finished chunks go into the reduce-scatter. As with tensor parallelism, the implementation has to start each chunk's transfer as soon as the chunk is ready.

With balanced routing, each device computes $\sim 12kBSEF/P$ operations. Each pass has a gather and a scatter of $\sim BSE$ values, $\sim 4BSE$ in all, so **the ratio is about $\boldsymbol{3kF/P}$**.

This method also cuts the expert weights each device stores, and its transfers can overlap with computation. But every device receives every token. All-to-all routing moves $\sim kBSE/P$ values per device in each transfer, so this method moves about $P/k$ times more per device. The gap shrinks as $k$ grows, and it can be smaller in practice, because all-to-all messages share network links and may need padding. Every device also needs room for all $BS$ tokens unless chunks are streamed, and a hot expert still slows the group.

## Summary

Each method splits different work, so each ratio depends on different numbers.

| Method | Split | Communication | Overlap | Ratio | Memory saved |
| --- | --- | --- | --- | --- | --- |
| Data parallelism | Batch | All-reduce $\partial W$ | Yes, except the last | $3BS/P$ | Activations |
| FSDP | Batch, model state | Two all-gathers of $W$, reduce-scatter $\partial W$ | By gathering ahead | $2BS/P$ | Activations, model state |
| Tensor parallelism | Feed-forward width $F$ | One all-reduce per pair in each pass | With chunking | $3F/P$ | Model state, some activations |
| Ring attention | Sequence | Neighbor transfers of $K,V$ | If each send fits in one block's compute | $2S/P$ | Activations |
| Ulysses attention | Sequence, then heads | Two all-to-alls | Not by default | $1.5S$ | Activations |
| Expert all-to-all | Experts | Two all-to-alls | Not by default | $3F$ | Expert weights, activations |
| Expert gather/scatter | Experts | All-gather, reduce-scatter | With chunking | $3kF/P$ | Expert weights |

Overlap and a high ratio help in different ways. Overlap stops a transfer from making computation wait. A high ratio keeps a transfer small compared with the computation, even when computation has to wait. Ulysses and all-to-all routing rely on a high ratio.

## Combining methods

Large training runs use several methods at once. They arrange the devices in a mesh and give each method one axis. Here, 8 devices form a $2 \times 4$ mesh, with tensor parallelism across each row and data parallelism down each column.

<DeviceMesh client:visible />

Each collective runs only within its group. A tensor-parallel collective involves the 4 devices in a row, and a gradient all-reduce involves the 2 devices in a column. Each ratio then depends on its own group size: with $P_t$ devices in a row and $P_d$ in a column, the ratios are about $3F/P_t$ and $3BS/P_d$. You can compute each ratio separately, but with a fixed number of devices, growing one group shrinks the other, and both transfers share the network.

## Appendix: collectives

Every method except ring attention uses these four collectives. Ring attention sends $K,V$ blocks only between neighbors. Each diagram shows 4 devices. The first three use a ring, in which each device sends only to the next device.

### All-gather

Every device starts with one piece and ends with all of them. Each device receives the $P-1$ pieces it doesn't have.

<Collective kind="all-gather" client:visible />

### Reduce-scatter

Every device starts with its own partial sum of every piece. Each device ends with one piece, summed over all devices. Each device sends $P-1$ pieces.

<Collective kind="reduce-scatter" client:visible />

### All-reduce

Every device ends with the full sum. A ring all-reduce runs a reduce-scatter and then an all-gather, so it moves twice as much data as either one.

<Collective kind="all-reduce" client:visible />

### All-to-all

Every device starts with one piece for each device, and each piece goes to the device it's for. Each device sends $P-1$ pieces and keeps one.

<Collective kind="all-to-all" client:visible />
